# Settings panels: plugins, skills and shared blocks

## UI settings

- The sidebar's Settings button opens the UI settings tab in `SettingsConfig`, the same dialog that owns Models, Skills, Plugins, and MCP. `/models` and `/mcp` open their respective tabs directly. The dialog grows up to 1440 × 1000 CSS pixels and keeps viewport margins and scrollable content on smaller screens.
- On phones, Settings keeps a 44px-tall **Close** button below its tab list. On browsers that deliver Android Back as a close request, Back dismisses the project-scope sheet or the Settings panel without navigating away from the chat.
- `components/FontSettings.tsx` offers separate interface/chat and monospace (code, tool output, terminal) font-name lists in the Fonts & layout section after Appearance, together with chat font size (which also sets the terminal's, hence its "Chat & terminal font size" label; client-platform.md) and content width; the Chat section keeps only behavior switches. Every row there has one shape: a header line (label, value, reset button in a fixed 28px column) over a full-width slider, so values and resets line up. A font row puts its name field between label and value, and its slider is the weight (100–600, step 100; `aria-valuetext` adds the weight's name). Both font rows share one grid (`subgrid`), so their name fields start at the same x whatever the labels' widths in each locale. The name field is drawn in the font it names, which is the preview; keep one short section description, no separate preview lines or per-control paragraphs. `hooks/useFontPreferences.ts` stores them only in the browser (`pi-ui-font-family`, `pi-mono-font-family`), applies changes immediately through `--font-ui` / `--font-mono`, and syncs other tabs. AppShell keeps the hook mounted so restoring a font never requires opening Settings or a chat. Empty input removes the override; the original stacks stay in `app/globals.css` as `--font-ui-default` / `--font-mono-default`.
- Font names refer to fonts on the **browser's device**, not the server; no enumeration, upload or remote download. `lib/font-preferences.ts` treats commas as separators, accepts optional enclosing quotes, quotes non-generic names as data, and always appends the default stack. Never interpolate font input into a stylesheet or accept it as executable CSS. Keep raw input whitespace while typing so multi-word names remain editable.
- Each font has a separate base weight (100–600 in steps of 100, default Regular/400; it stops at 600 because headings and labels use 600 and bold text, highlighted bold and the terminal's bold use 700, so a heavier base would outweigh them), stored as `pi-ui-font-weight` / `pi-mono-font-weight` and applied through `--font-ui-weight` / `--font-mono-weight`. Missing/invalid stored weights use 400; saving 400 removes the override. Each reset clears that font's name **and** weight in one update, not the other font or chat size/width. The UI weight is inherited by ordinary interface/chat text; code/pre, highlighted code (including its inline theme styles), source-view line numbers and diffs use the mono weight. Headings, Markdown bold/inline code inside emphasis, and other explicitly weighted labels keep their original weights; do not blanket-override them with `!important`.
- General's Sidebar section (after Chat) chooses where the desktop sidebar shows the file browser: below the sessions (default) or in a tab of its own, as two options in the send key's look (`settings-send-mode-option`), with "Phones always use tabs." under them (`aria-describedby`; `.settings-chat-options + .settings-general-description` turns a section's introduction into a note under its options). `hooks/useFilesPlacement.ts` keeps it per browser (`pi-web:sidebar-files-placement`; anything but `tab` reads as `below`) through `useSyncExternalStore`, so the server and hydration render `below` and the stored choice follows; it follows another tab through `storage` events and reads the key again when a first consumer subscribes, since nobody listened meanwhile. A blocked storage still applies the choice for the page. `SessionSidebar` reads it too and switches live, without remounting the explorer or the tree (sessions.md, the toolbar row and the two layouts); on a phone the choice is kept but the tabs show.
- General's Chat section also has "Show cost alongside subscription usage" (`hooks/useShowCostWithUsage.ts`, per browser, key `omp-show-cost-with-usage`, off by default). When the model's account reports subscription usage, cost is hidden from the stats bar, session popover and per-request lines (`hideCost` in `AppShell`/`ChatWindow`); the switch keeps it visible for metered plans.
- Appearance → **Chat animations** is on by default. Its duration is 0.8 seconds by default and adjustable from 0.4 to 2 seconds. Both settings are per browser and apply immediately; system reduced motion always wins. Off removes the live message, tool, token-flow, and composer effects without hiding their static status cues. In **Token display → Flow**, the input rail draws toward the model icon and reveals it on arrival. Once the reply starts, the output rail draws from the icon toward the reply. Sparks repeat on the active rail after it finishes drawing. Saved history shows the completed wires without replaying the animation. Process details grow and shrink at the same speed, using the same duration in both directions.
- Process details stay mounted and visibly clip down before the collapsed summary replaces them. Cards arriving in the same batch grow from zero layout height in transcript order. Active commands orbit in the warning color; streaming output orbits in the accent color. Replies retain a faint accent border distinct from thinking when motion is off. Wire geometry is read before applying SVG changes, and unchanged paths are left alone.
- In Flow mode, finished process folds open and close from either end. Their brackets widen, the contents expand or compress, then the brackets narrow again. Each phase takes half the chat animation duration. In-progress steps stay open without fold controls until the next chat input or output.
- Streaming prose fades in batches. Each batch finishes before the next begins, and the last fade finishes before the saved reply replaces the live one. Tool cards have a separate entrance queue. The model icon's spark orbits from waiting through output, and the current thinking block's spark repeats until the model moves on. Code blocks keep the existing streaming presentation.
- Final replies show a **Files written** count in the footer. Open it to see the paths from successful file-writing tools in that turn and preview a file. The list floats over the transcript (as a bottom sheet on phones), so it does not reroute the token wires.
- Expanded edit cards highlight their available JSON or patch preview while the call streams. Large previews stay plain while streaming to limit tokenization work. Edit, patch, and write cards keep their sparks moving while their input streams.
- Appearance → Token display is saved per browser. **Flow** shows model request and handoff wires. A collapsed gap with model requests is drawn as one turn marker, with the hidden requests' input, output, cache read and cache write totals. **Text** keeps token counts without wires. **Off** hides counts without changing cost visibility or session totals.
- Input includes prompts, steering, tool results and model-facing job updates; assistant chat, thinking and tool calls belong to output. A tool call is linked to its result by id, not by putting its result on the output rail. The model row carries the request time; the handoff carries the recorded end time (or the compaction timestamp). Folds have no handoff timestamp.
- User message wires meet the top and bottom edges at 75% of the transcript row, not 75% of the bubble. Short bubbles in Flow mode stretch just far enough to reach that rail.
- Flow appears while waiting for the model, before the first chunk. Output is marked as estimated when it starts arriving; input and cache counts wait for final usage, and the live tokens-per-second badge sits on the output line.
- Flow uses the SDK's per-response usage. Cache write is input the provider stored in its cache, so it sits on the input side above the wire beside new input (`W 1,744 + In 2`), with cache read below it; output stands alone on the output side. Cache read and cache write counts appear only when non-zero: a zero cache-write count is not proof that nothing was cached, since omp uses zero when the provider omits write accounting. The browser cannot derive writes from cache hits.
- Chat expansion defaults are per browser. Thinking and compaction summaries can start collapsed or expanded. Tool blocks also offer “failed only”; process details offer “automatic” (collapse gaps between chat boxes, keep the unfinished tail open). A manual choice takes precedence over the default. Opening a card does not reveal oversized output.
- UI settings → Tool display has two per-browser opt-ins: compact JSON for nested tool arguments, and compact Read headers with Markdown previews for eligible Read results and expanded skill commands. File Read cards use omp's display body when available, so model-only snapshot lines and footer notices don't enter syntax highlighting, even with Markdown previews off. Show raw exposes the original result. Neither setting changes shell stdout or the saved transcript.
- UI settings → Tool display also formats Python eval source (#62), off by default, per browser (`hooks/usePythonFormat.ts`, key `omp-python-format`, one JSON object). Python's indentation is syntax, so nothing is reflowed by the browser: `POST /api/format/python` (`lib/python-formatter.ts`) pipes the cell through `ruff format` or `black` if the server machine has one (probed with `--version`, cached 10 s; `GET` reports which). The setting picks `auto` (ruff, then black) or one of them. The cell is placed at `<session cwd>/eval-cell.py` through `--stdin-filename` with the process cwd set there, so the project's own `pyproject.toml`/`ruff.toml` applies; `cwd` must pass `requireAllowedCwd`, and without one the formatter runs in the temp dir. No shell is involved. Invalid code (non-zero exit), `%` commands, cells over 100,000 characters and streamed input (the card has no parsed code until the call completes) are shown as written; the browser asks once per source (`formatEvalPython` caches the answer until reload, so a newly installed formatter or edited config shows after a reload). Eval cards carry no line numbers, so formatted and raw views need no numbering rule; **Show raw** exposes the original. Direct and bash-mounted eval cards share `EvalToolCode`, which takes the session cwd from `BlockView`.
- Grep headers highlight the pattern; case, gitignore, and offset badges are green when active, red when off, and grey for explicit nulls. Semicolon-delimited paths appear as plain lines. Glob puts the search scope, hidden-file and gitignore icons, and result limit in the header. Eval uses language and kernel-reset icons, and displays elapsed seconds over the requested limit (`∞` when disabled). JavaScript eval source is formatted for display only; **Show raw** floats at the right of formatted eval source and Read previews. Recall, LSP, and Read omit arguments already shown in their headers. Read preview metadata keeps the fetch method, MIME type, notes, and any stripped snapshot tag or skill provenance; write acknowledgments omit the write snapshot tag without changing the recorded result.
- Eval’s reset icon follows the same colors as Grep’s boolean flags: green starts a fresh kernel, red reuses it (`false` or omitted), and grey marks an invalid `null` argument.
- Glob uses the same flag colors for hidden files and gitignore. Task cards show the requested isolation mode, with counts by mode for a batch. Browser `open` cards show explicit `headed` and `persist` overrides only; omitted values may use settings or preserve the tab's existing state.
- General's Appearance section, under the themes, sets the prompt-cache marker (#58; `hooks/usePromptCacheIndicator.ts`, per browser, key `omp-prompt-cache-indicator`, one JSON object). Which sessions show one: none, live sessions only, or "infer from last time" (also sessions nobody has open, read off their transcripts; the default, as the terminal shows a reopened session's). How it is drawn: "match terminal" (dim while warm, struck through in `--warning` once cold) or "gradient by time left" (`--success` mixed into `--warning` by the share of the lifetime left, struck through in `--danger` once cold, so a lapsed entry never reads as an almost-lapsed one). A switch dims an inferred status and adds a question mark (off by default). See sessions.md, Prompt-cache marker.
  Set **Inferred cache timeout (minutes)** to give inferred entries without an omp timeout a finite lifetime (for example, 30 for Codex). Leave it blank to keep omp's estimate. This only changes what the browser displays; it does not change provider retention or cache warming.
- ChatInput remeasures an existing draft when the interface font or weight changes. TerminalPanel subscribes in its existing lifetime effect, updates xterm's family and normal weight (its bold stays xterm's default 700, above every base weight) and refits, never restarting the terminal or its SSE stream for a font change.

## Plugins and skills
- `/api/plugins` uses pi's `SettingsManager` + `DefaultPackageManager` for global/project package install, remove, update, enable and disable; disabling writes empty `extensions/skills/prompts/themes` arrays to the package entry. Every POST drops the provider routes' shared runtime, since a package can add or drop a provider ([models.md](models.md), Auth and model config).
- Plugin update checks run npm and Git with the project-command environment policy (ADR 0001); npm configuration and `GIT_TERMINAL_PROMPT=0` remain available.
- `/api/skills` lists through `DefaultResourceLoader`, so settings paths, package skills and project `.agents/skills` appear as the runtime sees them. The loader takes `noExtensions: true` (`lib/skills-service.ts`, #1226): extensions add skills only through `resources_discover` at `session_start`, which a listing never runs, so importing them added nothing and blocked the event loop on every Skills open, skill click and slash-palette open. Skills an extension discovers never showed there, before or since. Even an empty extension load re-keys the SDK's one-cwd factory cache, so a listing for a folder other than the running sessions' still makes their next start re-import. The detail pane lazily reads a selected skill through `/api/skills/content` and renders its post-frontmatter instructions as Markdown; that route permits only an exact file path returned by the same runtime loader and caps the regular-file read at 1 MiB, rather than becoming a general Markdown-file reader. Toggling a skill edits only the `disable-model-invocation` frontmatter key of its `SKILL.md`, so user formatting survives, and `PATCH /api/skills` edits only `.md` files (its roots also hold `auth.json`, settings and project files). `/api/skills/install` shells through `npx skills add ... --agent pi`; project installs run in the selected cwd.
- Skill install, update and search subprocesses also apply the project-command policy and continue to filter credential-like host variables before running `npx`.
- **Skill documents.** A local link in the instructions (`MarkdownBody`'s `onNavigateLink`) opens that file in the same Instructions field. `resolveSkillLink()` resolves it from the linking document's folder, as pi resolves a skill's relative paths; `SkillDetail` keeps a stack of the documents opened, the last one shown under one Back button and its relative path. Switching skills remounts `SkillDetail`, emptying the stack. A link or Back brings the field's top, or the `#heading`, into view once the document shows: Back lands at the previous document's top, nothing saves a scroll position. A link to the skill file itself reads it without `document`. The client refuses nothing: an absolute path or a `..` past the folder goes to the route, whose message shows under Back.
- `/api/skills/content`'s optional `document` is a path in the loaded skill's `baseDir` (pi's dirname of the skill file): relative, without `..`, `\`, `:` or NUL, `.md`/`.markdown` by name and by real path, inside the folder after symlinks (`isExistingPathWithinRoots()`), a regular file up to 1 MiB. One stat before the bounded read answers a FIFO or a directory with 400 and a larger file with 413; a missing file is 404, a link out of the folder 403, and no refusal or failed read names a path. Without `document` the route reads the loaded file exactly as before.
- **Group switches.** Each sidebar group of the Skills, Plugins and MCP panels (a skill scope, a package scope, an `mcp.json`; not standalone extensions) has a `ConfigSidebarGroupSwitch` in its heading row, so the 190px phone sidebar loses no height. As with the Models provider switch, it is on only while every row is: a partial group reads as off beside its `n/m` count and one click completes it. A panel whose group can hold rows its switch never turns on passes its own `checked` (MCP: `mcpGroupSwitchChecked()`), or the switch stays off for good. One request carries the list (`PATCH /api/skills` `filePaths`, `POST /api/plugins` `packages`, `POST /api/mcp` `set-enabled` `servers`) and answers per item, so a refused row does not stop the rest; what was left undone shows under the heading (`ConfigSidebarGroupStatus`). An entry already in the requested state is left alone; enabling keeps an entry's own keys such as `autoload`. `SettingsManager` never throws a failed load or write (`flush()` resolves), so the bulk plugin path reads `drainErrors()`, or an unreadable settings.json would report success. Disabling empties the four resource lists and keeps no filters, so a group switched off leaves an enabled filtered package on (the SDK reports every object entry as `filtered`) and says so; the bulk route refuses it.

## Shared blocks
- Panels are built from the shared blocks in `components/SettingsUi.tsx` (`ConfigScopeTag`, `ConfigScopeSwitch`, `ConfigSaveTarget`, `ConfigAddSourceHeading`, `ConfigAddSourcePanel`, `ConfigDetailGrid`, `ConfigFooterStatus`, `ConfigTrustNotice`), `itemsToSwitch()` in `components/settings-ui-helpers.ts`, and `lib/display-path.ts`; a new settings section reuses them instead of copying a panel. `SettingsUi.tsx` takes every word as a prop and holds no state, so it renders outside the i18n provider; panels pass `t()` strings.
- **Every add pane chooses global or project in one place:** a `ConfigSaveTarget` (scope switch aria-labelled `config.saveTo`, plus the path that choice writes to) first under the pane's title, where a detail pane shows its `ConfigScopeTag` and path. Skills, Plugins and MCP get it through `ConfigAddSourceHeading` (title, the catalog links at its right, then the save target); Sub-agents put it in the detail header in place of the tag while creating. The submit button stays where its flow needs it (Install under the source box or on each skill result, Save in the footer, Add at the end of the MCP form), with why it waits beside it, not under the save target. The path is shown whole, never cut short: it wraps after a separator (`<wbr>`), then anywhere. Sub-agents offer both scopes whatever the folder's trust: profiles are not project resources that wait for it.
- **Why a control is unavailable is visible text** — a scope switch's `disabledReason` (under the switch's whole line, so controls passed as its `children` stay level with it), the note under a detail header, a footer summary that opens its diagnostics — never only a `title` tooltip, which a touch screen cannot show.
- Skills and Plugins take AppShell's project `trust` and reload in place after a decision. Visited project tabs stay mounted and are keyed by cwd, not trust, so refreshing their data does not discard pane state. Plugins also receives the active session's runtime binding for reloads.

## hand-edited agent settings

- before each non-duplicate `prompt` submission, `AgentSessionWrapper.send()` awaits `inner.settings.reloadFromDisk()` inside serialized prompt admission. this refreshes the retained session's global, project, and explicit config-overlay layers without replacing the settings object or discarding runtime overrides.
- a parse or validation failure rejects the submission before the sdk prompt starts and leaves the previous settings intact. fix the file and resubmit; a failed reload does not record a prompt deduplication fingerprint.
- this is a temporary workaround for [#12](https://github.com/flowtender/omp-frond/issues/12), not live watching. edits are applied at the next prompt submission, not automatically during an existing turn. separate `steer` / `follow_up` commands and extension-injected continuations do not trigger this refresh. refreshing settings does not reconstruct resources loaded at startup, such as model/tool registries.
- the installed sdk allows `startWatching()` only on its persisting process-global instance; `cloneForCwd()` creates independent snapshots for other working directories. the replacement sequence is [#15: upstream scoped-watching support](https://github.com/flowtender/omp-frond/issues/15), then [#16: omp-frond watcher lifecycle integration](https://github.com/flowtender/omp-frond/issues/16), then [#17: removal of the prompt-time refresh](https://github.com/flowtender/omp-frond/issues/17). each step depends on the previous one.
